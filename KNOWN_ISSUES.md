# Known Issues and Limitations

## Security and trust model

CACAO is a research tool intended for use within a trusted private network. The HTTP API (`server.py`) does not authenticate requests — anyone who can reach port 8003 can create problems, run optimizations, and read or delete files inside `problems/`. The engine compiles and executes LLM-generated CUDA code under the server user's identity.

**Do not expose port 8003 to the public internet, and do not run CACAO on `problem.yaml` files from untrusted sources.** The `eval()`-based size expressions in `utils/python_ref_runner.py` are sandboxed only with `{"__builtins__": {}}`, which is not a strong sandbox; a crafted expression can escape and execute arbitrary Python in the engine process.

## Functional limitations

- **Python 3.10 is what the setup script provisions.** The environment is built and tested on 3.10; nothing here has been verified on newer interpreters. The old reason — the `pyktt` pybind11 bindings being pinned to the 3.10 ABI — no longer applies: the engine drives KTT through a compiled C++ driver and the bindings are neither built nor imported.
- **Single-host only.** Concurrent tuning on multiple GPUs of the same host is supported; cross-host scheduling is not implemented.
- **Cross-process branch config writes are not serialized.** If the API server and the engine subprocess both write to the same `branch.json` (e.g. user changes `max_iter` via the UI while the worker is mid-iteration), the later writer wins and the earlier change can be silently lost. Workaround: retry the config change. A proper fix requires cross-process file locking on `branch.json`.
- **A run that dies at startup is invisible in the UI.** `POST /api/problems/<name>/run` returns `200 OK` as soon as the optimizer process is forked, before the child has imported the engine. If the child then dies — an `ImportError`, a missing API key, an unreadable problem — the frontend has already set the status to `running` on that `200` (`Toolbar.tsx:65`), and the next `/tree` poll finds nothing running and flips it back. The symptom is a Run/Rerun button that flashes and reverts with no error toast, looking as though the request never fired; the traceback reaches only the server's stdout. Workaround: read `server.log`. A proper fix requires the API to learn whether the child survived startup — either `/run` waiting for the child to signal readiness before returning, or a dead-run state the tree/status endpoint can report and the UI can render.
- **The server must be restarted after engine code changes.** `api/optimizer.py` starts runs with `multiprocessing.Process`, which uses `fork` on Linux, so each child inherits the parent's already-imported modules rather than re-reading them from disk. A long-lived `server.py` that imported a module before it changed will keep handing every forked run the stale version, and the run dies on an import that succeeds in any fresh interpreter (`cli.py` is unaffected for this reason). This bites hardest after a branch switch or merge that rewrites engine files under a running server. Workaround: restart `server.py` after changing anything under `engine/`, `nodes/`, or `utils/`. Combined with the silent-startup-death issue above, the only visible symptom is the flashing button.
